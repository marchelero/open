## Context
El reporte `docs/reports/2026-10-06-open-vs-agentes-comparativa.report.md` §11.3 #7 propone: *"Resumen embedding de cada skill (generado 1 vez) para que el router lea el resumen y no el SKILL.md completo."* Es una idea "fuera de ambos packs"; **no** es parte de la fusión (§8) ni de los PRDs de Fase 1–3. Se aborda como extra aislado.

Esta idea, tal como está redactada, **parte de una premisa falsa** para este pack. El motor de routing ya existe (`route-engine.js`, BM25 + tokenizer) y **nunca abre el cuerpo de un `SKILL.md`**: `catalog.js` enumera el catálogo y `parseFrontmatter()` extrae solo `name` + `description` + `triggers`. No hay "SKILL.md completo" que evitar en el ranking. Un "resumen embedding" añadiría dependencia de modelo/red (viola zero-deps) sin mejorar el ranking: §11.2 #4 (router semántico) es un extra distinto y diferido.

Los costes **reales y medibles** que el pack sí controla hoy (cifras de `measure-tokens.js --json`, 2026-10-07):

| Componente | Coste actual | ¿Lo controla el pack? |
|---|---|---|
| Catálogo en system prompt (`description` de 78 skills + 67 agents) | **10 085 tok** (40 338 B) | **Sí** — es texto de frontmatter que el pack escribe |
| Router `SKILL.md` (hot path, cada dispatch) | **6 413 tok** | Sí, pero es lógica de routing, no descripciones |
| Parseo del catálogo en cada dispatch | **145 lecturas de archivo + parseo** | Sí — hoy `route()` re-lee los 145 ficheros cada vez |
| Boot | 1 407 tok → `bootStatus` GREEN | Sí |

Del catálogo, **101 de 145 `description` superan 200 B** (peores: `xlsx` 939 B, `router` 907 B, `prd-agent` 842 B, `docx` 820 B, `pptx` 725 B). Ese texto alimenta el system prompt **en cada turno**, y es la palanca de tokens más directa (§10.5 #4). En paralelo, resolver un skill re-parsea los 145 ficheros aunque el resultado sea determinista y cacheable.

## Objective
Reducir de forma **medible y sin dependencias** el coste de contexto del catálogo de skills/agents y el coste de resolver un skill, mediante (1) un **índice condensado regenerable** que el router consume sin releer cada `SKILL.md`, y (2) un **reporte de coste** que permita adelgazar las descripciones que hoy dominan el catálogo — preservando intactos el router, la batería (E1–E17) y las gates de CI.

## Approach decision (justificado)
Cuatro enfoques evaluados:

- **A. Resumen *embedding* literal — RECHAZADO.** Requiere modelo/red/vector store (viola zero-deps, Node 18) y no aporta al ranking porque el motor ya no lee cuerpos. §11.2 #4 (router semántico) es el extra correcto para eso y queda fuera de alcance.
- **B. Índice condensado (digest) cacheado — RECOMENDADO.** Un artefacto JSON derivado (name + descripción de 1 línea + triggers + bytes + hash) generado **una vez**; el motor de routing lo consume leyendo 1 fichero en vez de re-leer+parsear 145 por dispatch. Zero-dep, determinista, sin cambio de comportamiento de ranking. El "resumen condensado" se obtiene de forma **determinista** (1.ª frase / recorte), no con embeddings.
- **C. Reporte de coste — RECOMENDADO como modo de B.** Ya se miden totales (catálogo/router) pero no *cuáles* descripciones son las culpables ni qué tan cacheable es el parseo. Exponer un ranking de descripciones por longitud convierte la medición en acción.
- **D. Adelgazar descripciones — RECOMENDADO (la ganancia real de tokens).** Es lo único que baja los ~10 K tok fijos del system prompt. Se aísla en su propio milestone porque toca 101+ textos y debe pasar el gate de routing.

**Decisión: B + C (un digest con modo reporte) y D como milestone de payoff.** Se descarta A explícitamente.
